从两台靶机入口看php2shell的两条利用链

vulnyx更新了一台hard难度的靶机，入口与群友出的靶机均为利用php2shell进行rce，故用ai撰写一小文以供复现和查阅

两台机器入口不同，但都靠 PHP 的 session.upload_progress 起步：

  • 192.168.56.251 phpblog —— Typecho 博客，Apache + PHP-FPM 8.4.24。入口是两个页面：/usr/themes/classic-22/submit/（投稿上传）和 /usr/themes/classic-22/status/（投稿状态）。
  • 192.168.56.252 BrokenTusk —— nginx + PHP-FPM 8.0.30。入口是一个 LFI：/vuln.php?page=...，源码就是 include($page)。

phpblog 走的是”会话格式错配 → 反序列化 → 析构函数执行命令”（仓库里的 C 链）；BrokenTusk 走的是”把 PHP 代码写进会话文件 → 用 LFI 把会话文件当脚本包含”（A 链）。下面先把 php2shell 的共同底座讲清，再分别给两台机器的复现步骤，命令全部可以直接复制。

1. php2shell 的底座：PHP 自己把文件名写进会话文件

1.1 session.upload_progress 做了什么

PHP 有个默认开启的功能，叫 upload progress，作用是让浏览器能看到上传进度条。只要 multipart 表单里带一个名字叫 PHP_SESSION_UPLOAD_PROGRESS 的字段，PHP 就会在你的业务代码执行之前自己 session_start()，然后把”正在传什么文件”写进会话文件。

会话文件路径是 session.save_path + /sess_<PHPSESSID>，默认 /tmp/sess_<PHPSESSID>。

关键在这：写进去的文件名是原样写入的，PHP 不做转义、不校验。所以攻击者控制了文件名，就等于控制了一小段”以后会被 PHP 自己再读回来”的字节。这条写入发生在请求最开头，不登录也能触发。

1.3 写这一步的三个前置条件

  1. session id 自己定。session.use_strict_mode 默认是 0，客户端给的 PHPSESSID 会被直接接受，不用猜。
  2. body 要先发够 5 KB。PHP 按 5 KB 一块（FILLUNIT）解析 multipart，只发完请求头、文件体一个字节都没到，FILE_START 事件不会触发，进度记录根本不会落盘。所以先发至少 5 KB 内容，再把连接挂住。
  3. cleanup 的两种处理。session.upload_progress.cleanup 默认 On，上传一结束记录就被删，所以默认情况下要”挂住上传”，在挂住期间完成后面的动作；如果目标关了 cleanup（phpblog 就是），记录会一直留在会话文件里，事后慢慢用。

1.4 这个洞的底层 bug（B/D/E 链才需要）

PHP 的 emalloc 分配失败时会走 zend_bailout()，一个 longjmp 直接蹦回请求边界，中间的清理全部跳过：

  • 半初始化的结构体、已释放还被引用的指针 → 单请求内 UAF，CVE-2026-109618；
  • 每个请求持有的全局变量被留在半截状态，常驻 worker 的下一个请求复用它 → 跨请求 UAF，CVE-2026-109619。

受影响版本 PHP ≤ 8.4.26、8.5 ≤ 8.5.11，修复版本 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12（commit 31c0ea7）。

3.2 为什么会执行命令

两种 session 处理器对 | 的理解不一样：

  • php 处理器把 | 当分隔符，格式是 键名|序列化值，读的时候按 | 切分；
  • php_serialize 处理器把整个数组一起序列化，| 只是普通字符。

所以 submit 页用 php_serialize 写出来的会话文件里，文件名带的一个 |，会被 status 页的 php 处理器当成”从这里开始是值”，把右边的字节丢给 unserialize()。

右边是 O:11:"TempCleaner":...，正好是前面加载好的类。对象构造出来之后，右边还有一串尾巴导致解析失败，PHP 走清理逻辑，把刚构造的对象销毁——__destruct 被执行，system('rm -rf ' . $path) 里的 $path 拼上 ;命令;# 就成命令执行。

4. 两条链并排看

同一个写入点，两种弹药，下游 sink 不同：

BrokenTusk (.252) A 链 phpblog (.251) C 链
写会话 upload_progress 文件名注入 <?php upload_progress 文件名注入 |O:
读会话 include($page) session_start() 的 php 处理器
前置 一个 LFI 写读 handler 不一致 + 已加载的析构 gadget
落点 PHP 直接执行代码块 反序列化对象 → __destruct → system
难点 会话路径、open_basedir、cleanup 时序 类没加载 / handler 一致 / 没发够 5KB

phpblog 没有 LFI，A 链用不上；BrokenTusk 的 include 不会反序列化，C 链用不上。php2shell 只负责”把攻击者的字节写进会话文件”，具体怎么变成 RCE，看目标下游是什么。

5. 防御，简单带过

通用：

A 链（BrokenTusk 这类）：include 参数做白名单映射，别直接拼 $_GET['page']；open_basedir 排除 /tmp、/proc。

C 链（phpblog 这类）：全站统一 session.serialize_handler，别按目录散落 .user.ini；不要在 session_start() 前加载带 __destruct/__wakeup 的类；危险类从 unserialize_allowed_classes 里拿掉；清理类别写 system('rm -rf '.$path) 这种拼接。

版本：升到 8.4.27 / 8.3.36 / 8.2.35 / 8.5.12，挡 B/D/E；A/C 不是版本问题，配置不改照样打。
