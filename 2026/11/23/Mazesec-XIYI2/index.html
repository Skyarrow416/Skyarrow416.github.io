端口扫描

复盘： 只有 22 和 8080 两个端口，攻击面非常窄。值得注意的细节是 TTL：22 是 64（直达宿主机协议栈），8080 是 63（少了一跳）——这一跳就是宿主机的 docker-proxy/NAT，说明 8080 实际是端口映射进容器的服务，而不是直接绑在宿主机上的。这个细节在扫描阶段就暗示了后面”打的是容器而不是宿主机”的结构，同时也预示了出网受限的可能性。RustScan 的速度优势在这里体现出来：先秒速定位端口，再交给 Nmap 做服务确认，省掉了全端口慢扫的等待时间。

泄露/actuator/heapdump

复盘： JDumpSpider 按”目标类”在堆里做模式匹配，各个 searcher 分别扫 DataSource、Shiro、UserPassSearcher 等特定 class 的实例字段。本次的收获全在 UserPassSearcher：AuthController 和 AdminController 两个字段的实例里直接躺着 dbPassword = lemonsseecc、passphrase = BuildingMaintenance2026!。关键坑：Java 的 String 在堆里是 UTF-16 存储，纯 ASCII grep 会全部漏掉——要么按 utf-16le/be 双编码搜，要么用 export-strings 把字符串原样导出再翻。JWT 签名密钥 0x64sdas55xad888al 就是从导出的字符串堆里翻出来的。

单引号直接报sql错误.

堆里 JDBC 开了 allowMultiQueries。GET /admin/report/search?q= 把 q 拼进 SQL，单引号闭合就能堆叠。库的 legacy 插件表挂着 lib_mysqludf_sys.so，注册成 sys_eval 就能在 MySQL 容器里执行命令

复盘： 单引号直接报错说明 q 是字符串拼接进 SQL（大概率套在 LIKE '%q%' 的模板里），没有预编译——错误回显本身就是注入点存在的铁证。接下来只需确认两件事：能不能堆叠（JDBC URL 里 allowMultiQueries=true 已在 heapdump 里看到，能），以及注入的执行身份是什么（JDBC 连的是 root，所以直接是 DB 最高权限）。两个条件齐备，这条 SQL 注入就能升级成”以 root 身份跑命令”。

复盘： 堆叠注入的固定套路：第一条 ' AND 1=0; 把原查询作废（避免 LIKE 报错中断整批），随后追加自定义语句，-- 注释掉尾部。这条探针 SELECT 了 legacy_plugins 表——这是题目埋好的路标：一张挂着 lib_mysqludf_sys.so（文件名直接写在 id 列）的”遗留插件表”。返回 JSON 里 results 是数组套数组，对应堆叠的每条语句各自的结果集——服务端把多条语句都执行并把结果分组返回，这让堆叠注入几乎等价于一个 SQL 控制台。

复盘： CREATE FUNCTION sys_eval RETURNS STRING SONAME 'lib_mysqludf_sys.so' 是 MySQL UDF 提权的核心一击：它让 mysqld 把 plugin 目录里的 .so dlopen 进自己进程，之后 sys_eval('命令') 就以 mysqld 的身份执行 shell 命令。能 CREATE FUNCTION 是因为 JDBC 连的是 root（SUPER 权限）。UDF 比 INTO OUTFILE 写文件稳得多：后者受 secure_file_priv 路径限制，UDF 只要 so 文件已在 plugin 目录即可，而镜像里预置好了，不需要额外上传。

抓包看一下验证的逻辑

rO0AB 就是 Java 序列化的魔数（0xACED0005 的 base64）。也就是说：提交口令的时候，服务端会对这个 Cookie 做 readObject()。口令在堆里已经拿到了，所以能一路走到 readObject 那一步。

复盘： rO0AB 是 Java 序列化流魔数 0xACED0005 的 base64 前缀，出现在 Cookie 里意味着服务端会把这个值 readObject() 反序列化。LabKey 对象本意是挑战-响应的 nonce，理应只在服务端生成和校验——但实现把整个 Java 对象图序列化后放 Cookie 回传给客户端，等于把 readObject 入口直接交给了攻击者。classpath 里的 commons-beanutils-1.9.4 在 heapdump 阶段已确认，CB1 gadget 可用。唯一需要验证的问题是：readObject 在口令校验之前还是之后执行——之后的话，错误口令会先 403 拦住，gadget 根本运行不到；实践证明是之前（后面用恶意 Cookie + 无效口令照样 500），gadget 无条件触发。

先确认口令是对的

复盘： 先用正确口令走一遍干净流程，确认 (1) 口令本身没错，(2) challenge 拿到的 nonce 会被放进 Cookie 带回去，(3) {"verified":true} 是成功路径的响应格式。有了这条基线，后面”换成恶意 Cookie + 同一个 passphrase”时，如果返回 500 就可以断定是 readObject 炸了（gadget 触发），而不是口令错了。

之后准备rce脚本，java反序列化的链子已经在heapdump中预先知道了

rce.py封装了三件事：生成 CB1 gadget、把 gadget 当 Cookie 发出去、以及用 bash 执行复杂命令。

两个坑先说：

  1. JDK9+ 跑 ysoserial 要加 --add-opens，否则 java.xml 模块不导出 TemplatesImpl 相关包，直接 IllegalAccessError
  2. Runtime.exec(String) 按空白切词，所以管道、重定向这类必须交给 bash；而 bash 那条命令本身不能有空格，用 brace expansion 绕：bash -c {echo,B64}|{base64,-d}|bash

复盘： 这段封装精巧，值得逐层拆：

gadget 生成端：gen() 每次调 ysoserial CB1，链尾是 Runtime.exec(cmd)。ysoserial 要放开 java.xml 和 java.base 的三个模块（--add-opens 三件套），否则反射 setAccessible 碰封装包直接 IllegalAccessError——这是 JDK9 模块化带来的固定阻力。

无空格命令：Runtime.exec(String) 按空白切 argv，管道 |、重定向 > 等 shell 特性根本不存在。解法是 bash brace expansion：bash -c {echo,B64}|{base64,-d}|bash——花括号展开成带空格的参数，但命令字符串本身一个空格都没有，可以安全地进 exec()。B64 是整条复杂命令的 base64，绕开所有特殊字符。

回显通道：容器连不出网（下面才确认，但先设计好方案）。exec_cmd() 把命令输出重定向到 /app/classes/static/{uuid}.txt，/app/classes 是 classpath 且其下 static/ 被 Spring Boot 映射为静态资源——8080 本身就是回显通道，轮询 GET /{uuid}.txt 读回结果，零新增端口。

复盘： Web 容器是双网卡（172.31.10.10 连 DB 网段，172.31.20.10 连 DC 网段），是两侧之间唯一的跳板，但出网被防火墙封死——/dev/tcp 探测攻击机 4444 端口超时返回 UNREACH，反弹 shell 这条路完全不可行。解法只有一个：从外部往里打正向隧道，复用已经映射出来的 8080 端口作为隧道载体。这就是接下来 Tomcat Valve 内存马 + suo5 方案的出发点：用 8080 承载 HTTP 隧道流量，攻击机通过 socks5 代理打穿内网，不需要任何新端口。

反弹不通，那就只能从外面往里打——开一条正向的 HTTP 隧道，复用已经映射出来的 8080。

用 MemShellParty 生成 Suo5 Valve 内存马

隧道分两半：服务端是挂在 Tomcat 上的 Valve，客户端是 suo5。先用 MemShellParty 生成服务端。

启动 MemShellParty（Spring Boot 程序，默认占 8080，改到 18080 免得冲突；JDK25 上要放开 java.xml 模块，否则生成序列化 payload 会 IllegalAccessError）：

复盘： MemShellParty 在攻击机本地起服务（18080 端口），只负责生成 payload，不与目标交互。本地是 JDK25，而生成 CB1/TemplatesImpl 序列化类要碰 com.sun.org.apache.xalan 内部包——JDK9 之后这些包被 java.xml 模块封装，必须 --add-opens 三件套（trax / runtime / java.util），否则反射 set 字段时直接 IllegalAccessError。这和前面 ysoserial 的 --add-opens、后面 javac 的 --add-exports 是同一个模块化封锁的三个面，所有涉及反射 Java 内部类的工具都要加。端口改到 18080 避开和目标 8080 的本地冲突。

调 API 生成内存马。参数含义：

  • server=Tomcat / serverVersion=9.0.83：目标中间件（版本从 heapdump 的 classpath 看到的）
  • shellTool=Suo5 / shellType=Valve：走 Suo5 协议、挂成 Tomcat Valve（Valve 在 pipeline 最外层，拦所有请求，比 Filter 稳）
  • targetJreVersion=52：目标 JRE 8，class 版本要 52
  • shrink=true：压缩字节码，压进 Tomcat 默认 8K header 限制
  • headerName/headerValue：隧道流量的识别特征。用 Referer 是因为业务不会覆盖它，http://mazesec.local/ 随便编一个本站不会发的值
  • injectorClassName：注入器类名，一会儿要上传这个类
  • packer=DefaultBase64：输出 injector 的 base64

复盘（内存马·生成参数）：每个参数背后都有具体理由：

  • server=Tomcat / serverVersion=9.0.83：内存马贴着中间件内部 API 写，版本不对 API 签名就会变，从 heapdump classpath 里的 tomcat-embed-core-9.0.83 直接抄，不能凭感觉填。
  • shellType=Valve：Tomcat 请求链是 Engine → Host → Context → Wrapper 四层 pipeline，每层挂一串 Valve。Valve 型内存马把自己插到最外层（Engine 级），所有请求都先流过它——比 Filter 型（要匹配 url-pattern）和 Listener 型（只在事件触发时活）更稳、覆盖面更广，后续 suo5 的隧道流量也会被正确接管。
  • targetJreVersion=52：生成的 injector class 要在目标 JRE 8 里被 defineClass，major version 必须是 52（JDK8）；攻击机本地 JDK25 默认输出 69，不往下降就报 UnsupportedClassVersionError。
  • shrink=true：压缩字节码。injector 的 packResult 解码后 24718 字节，会通过 CB1 RCE 分块上传落盘，不经过 HTTP header；但真正后面塞进 Cookie 的 Loader gadget 只有 2169 字节，shrink 是为了让内存马本体尽量小，以防未来有场景需要把 injector 本体也塞 header（本题没触发）。
  • headerName=Referer / headerValue=http://mazesec.local/：Valve 里的流量识别暗号——只有带这个 Referer 的请求才被内存马劫持当隧道流量处理，其他业务请求正常放行。用 Referer 是因为业务自身不会带一个指向不存在域名的 Referer，等于私有特征。
  • 两段结构：packResult 是 injector（Suo5Inj，负责在 JVM 里把内存马 defineClass 并挂 Valve），shellClassName 是随机名的内存马本体（已内嵌在 injector 里），名字每次随机生成是为了对抗基于类名的检测。

返回里有两个东西：

  • packResult：injector 类的 base64（这就是我们要上传的 class 本体）
  • memShellResult.shellClassName：真正干活的内存马类名（每次随机生成，不用管）

写 TemplatesImpl 载体

它的核心就一个 static 块：

复盘（内存马·为什么要 TemplatesImpl）：这是整个内存马方案最关键的设计，值得完整拆一遍因果链。

问题：injector（Suo5Inj.class）已经落到磁盘 classpath 上，但需要有人在运行中的那个 Tomcat JVM 里 Class.forName 把它实例化，它才能挂 Valve。手里的 CB1 gadget 只会 Runtime.exec(cmd)——新起子进程，子进程里没有 Tomcat 的 StandardContext，Valve 根本挂不上去；哪怕用 CB1 执行 java -cp /app/classes ... 再起一个 JVM 也是一样的死路（见”卡住的点”第 4 条）。

解法：TemplatesImpl 自带”在当前 JVM 里 defineClass 并实例化“的原语。调用链：PriorityQueue.heapify() → BeanComparator.compare() → PropertyUtils.getProperty(templates, "outputProperties") → TemplatesImpl.getOutputProperties() → newTransformer() → getTransletInstance() → defineClass(_bytecodes[0]) → newInstance()。整条链在 readObject() 里同步执行，而 readObject 是在 Tomcat 自己的 JVM 里调的——所以 defineClass 出来的类、以及 newInstance() 触发的 static 块，都在 Tomcat 进程空间里运行，可以访问 Thread.currentThread().getContextClassLoader() 找到 StandardContext，把 Valve 插进去。

Loader 的结构：继承 AbstractTranslet 是硬要求——getTransletInstance() 源码里会把 newInstance() 结果强转成 AbstractTranslet；实现两个空 transform 是因为 AbstractTranslet 是抽象类，不实现抽象方法编译就过不了。static 块里 Class.forName("lab.ctf.Suo5Inj").newInstance() 一行负责从 classpath 把已上传的 injector 类加载进来并触发其构造函数——injector 的构造函数里做的就是 defineClass 内存马本体 + pipeline.addValve()。

分两段（上传 injector + 加载 Loader）而不是把内存马整块塞 gadget 的原因：一个完整的内存马 class 加上 gadget 包装，base64 后超过 Tomcat 默认 8192 字节 header 上限，直接 400 截断；拆成”大文件走 RCE 落盘，gadget 只装一个 ≈1KB 的加载器”，Cookie header 只有 2169 字节，轻松通过。

复盘（CB1 链构造顺序）：手工链每一处顺序都有严格的理由：

  1. 先 add(new BigInteger("1")) 再换 property：PriorityQueue.add() 入堆时会真正调用 comparator。如果此时 property 已经是 outputProperties，comparator 会试图对 BigInteger 调 getOutputProperties()——BigInteger 没有这个方法，直接 NoSuchMethodException 崩掉，序列化对象都生成不了。所以先把 property 设成 lowestSetBit（BigInteger 有这个属性），两个 BigInteger 顺利入堆，再反射把 property 改成 outputProperties，再把 queue 底层数组的两个元素换成 TemplatesImpl。生成端的 compare 和消费端的 compare 要用不同的 property 值，这是整个手工链最容易踩的坑。

  2. _bytecodes 装 Loader52 的字节码：TemplatesImpl 在 getTransletInstance() 里遍历 _bytecodes 数组，把每个元素当 class 字节码 defineClass，然后 newInstance() 触发 static 块。装 Loader52 而不是直接装 Suo5Inj，是因为 Suo5Inj 超过 8K header 上限；Loader52 只有 1028 字节，序列化后 2169 字节，轻松通过。

  3. _name 随便非空，_tfactory 必须给：_name 为空时 getTransletInstance() 会走另一个分支直接返回 null，不会走 defineClass；_tfactory 是 newTransformer() 里要用的工厂，必须给一个可序列化的实现（TransformerFactoryImpl 刚好可以）。

  4. queue 底层数组替换：PriorityQueue 有一个私有 Object[] queue 字段，add() 操作改的是这个数组。反射 getField(queue, "queue") 拿到它再改 arr[0] = arr[1] = templates，就绕开了会触发 compare 的 offer() 方法，直接替换底层存储。反序列化端 readObject 会调 heapify() 触发比较，这时 property 已经是 outputProperties，链子炸响。

用 MIT kvno 做 S4U

配好 RBCD 以后，正常做法是 impacket 的 getST -impersonate Administrator。但这台 Samba 上走不通，会报 KRB_AP_ERR_INAPP_CKSUM——是 TGS-REQ 的 authenticator checksum 类型对不上。

换 MIT krb5 自带的 kvno（1.19 以后支持 S4U，checksum 对得上 Samba）：-I 做 S4U2Self，-P 接着做 S4U2Proxy。

复盘： KRB_AP_ERR_INAPP_CKSUM 是 impacket 和 Samba 之间的兼容性 bug：impacket 在 TGS-REQ 的 authenticator 里使用了 Samba 认为不合适的 checksum 算法类型，Samba 拒绝了请求。MIT krb5 自带的 kvno 工具（1.19 版以上支持 S4U 扩展）用的 checksum 类型和 Samba 兼容，是这个场景的正确解法。

kvno 两步工作原理：S4U2Self（-I Administrator）以 CTF01$ 的 TGT 为凭据，向 KDC 申请一张”Administrator 访问 CTF01$ 自身”的可转发 ST（服务票据的主人是 Administrator 而不是 CTF01$，这张票是后续 S4U2Proxy 的输入）；S4U2Proxy（-P）把上一步的可转发 ST 作为证据，申请一张”Administrator 访问 host/dc01.corp.local + cifs/dc01.corp.local“的正式服务票。全程不需要 Administrator 的密码，完全靠 RBCD 配置给 CTF01$ 的信任关系。--out-cache admin.ccache 把结果票据保存到独立 ccache，不影响 CTF01$ 的 TGT。

复盘： admin.ccache 的 principal 是 Administrator@CORP.LOCAL，服务票覆盖了 host/ 和 cifs/。前者给 SSH GSSAPI 用，后者给 SMB 验证用。先用 cifs 票跑 nxc SMB 是最快的健全性检查——能认证说明 KDC 和 Samba 都接受了 S4U 链生成的票据，admin.ccache 是有效的。

GSSAPI SSH 登 root

sshd 只开 GSSAPI，.k5login 只认 Administrator@CORP.LOCAL。

这里有个坑：不能用 proxychains 跑 ssh。proxychains 是 LD_PRELOAD 劫持 socket 调用，会把 GSSAPI-MIC 的字节流搞坏，客户端算的 authenticator 服务端验不过，直接 Permission denied。正确做法是用 ssh 自己的 ProxyCommand 配 socat，只代理这一条 TCP，主机名保持 FQDN（SPN 才不会飘）：

复盘： GSSAPI-MIC（Message Integrity Check）对底层字节流的完整性很敏感——它计算一个基于传输数据的 MIC，如果 LD_PRELOAD 在 socket 层插入了额外字节或改变了缓冲区边界，服务端算出的 MIC 和客户端不一致，直接认证失败，报 Permission denied (gssapi-with-mic)。必须用 ssh 原生 ProxyCommand：socat 只做纯 TCP 转发（SOCKS5-CONNECT:127.0.0.1:1080:%h:%p），不干预 TLS/GSSAPI 层；ssh 自己管 GSSAPI，socket 字节流完全透明。

-o GSSAPITrustDns=no 防止 ssh 相信 DNS 返回的主机名（内网 DNS 在隧道另一侧，可能不可信）；-o PreferredAuthentications=gssapi-with-mic 强制只走 GSSAPI，不让 ssh 自作主张降级到密码认证。连接目标必须用 FQDN dc01.corp.local，因为 Kerberos SPN 是 host/dc01.corp.local@CORP.LOCAL，主机名不匹配 SPN 就会找不到对应的票据。

复盘： uid=0(root) 且 dc01 是域控——整条链走完。SSH 进来即 root 是因为 .k5login 里写的是 Administrator@CORP.LOCAL，这个 Kerberos principal 对应的 Linux 用户就是 root（Samba 的 winbind 把域 Administrator 映射到 uid 0）。

总链路回顾：heapdump 把 JVM 内存变成凭据库（JWT 密钥 + DB 密码 + 2FA 口令）→ JWT 伪造进 ADMIN → SQL 注入 + UDF 拿 DB 容器 root（user flag）→ 2FA Cookie 反序列化 CB1 拿 Web 容器 RCE → 内存马 + 正向隧道把 8080 变成内网跳板 → 空会话枚举 + 无预认证 Kerberoast 拿 lemon → ACL 链（ForceChangePassword → CreateChild → WriteProperty RBCD）→ S4U 冒充 Administrator → GSSAPI SSH 进域控（root flag）。每一层都复用上一层的产出，没有一步是孤立武器堆砌。

几个容易卡住的点

  1. heapdump 里的 String 是 UTF-16：纯 ASCII grep 会漏掉所有凭据，必须按 utf-16le/be 搜。
  2. ADMIN 票的 sub 要写 admin：只改 role 不改 sub 会 403。
  3. 内网容器连不回攻击机：只能用正向隧道（suo5），不能指望反弹。
  4. 内存马必须在 Tomcat 的 JVM 里加载：java -cp xxx 是独立进程，Thread.getAllStackTraces() 里没有 Tomcat 线程，会 context not found。要用 TemplatesImpl 在 readObject 里 defineClass。
  5. JDK9+ 跑 ysoserial / 编 AbstractTranslet 要 --add-opens/--add-exports：否则 java.xml 模块不导出，直接 IllegalAccessError。
  6. class 版本号要对：javac 25 编出来的是 69，目标 JRE8 要 52。简单类可以改 class 文件第 7 字节降版本。
  7. Tomcat 默认 header 上限 8K：大 gadget 会被截断。这次 gadget 只有 2169 字节没触发问题；超了要压字节码或先改 maxHttpHeaderSize。
  8. proxychains 会破坏 GSSAPI-MIC：SSH 必须用 socat 做 ProxyCommand。
  9. proxychains 别开 proxy_dns：Kerberos 的域名解析会被代理搞死，kinit 报 Cannot find KDC。
  10. Samba 不认 impacket 的 getST：用 MIT kvno 做 S4U。
