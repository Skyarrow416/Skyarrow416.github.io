针对 Domain Controller 的约束委派攻击

为了伪造域管（Administrator）去访问 DC 的 C$ 共享 ，攻击需要利用 Kerberos 协议的两个关键扩展协议：S4U2Self (Service for User to Self) 和 S4U2Proxy (Service for User to Proxy)。

  • 前置条件：获取机器账户凭证

    操作:使用 Mimikatz 从 172.22.2.16 的内存中导出了机器账户 MSSQLSERVER$ 的 NTLM Hash (f496fe749b403f432a5e2c0d49113a29) 。

    • 原理：只有拥有该服务（机器）账户的凭证，才能以该服务的身份向 KDC（密钥分发中心）发起委派请求。

  • 第一步：申请机器账户的 TGT

    操作：执行 Rubeus.exe asktgt /user:MSSQLSERVER$ /rc4:f496... 。

    原理：利用刚拿到的 NTLM Hash（RC4 加密），向域控伪造正常的 AS-REQ 请求，换取 MSSQLSERVER$ 这个机器账户的 TGT（票据授权票据） 。

  • 第二步：S4U2Self (服务代表用户向自己申请票据)

    操作：包含在 Rubeus.exe s4u /impersonateuser:Administrator ... 命令的底层执行中

    原理：MSSQLSERVER$ 拿着自己的 TGT 告诉 KDC：“域管 Administrator 正在访问我，请给我一张 Administrator 访问我自己的 TGS（服务票据）”。由于 S4U2Self 的特性，KDC 不需要验证 Administrator 的密码，直接返回一张以 Administrator 身份访问 MSSQLSERVER$ 的 TGS。且此票据带有 forwardable（可转发）属性 。

  • 第三步：S4U2Proxy (代表用户向其他服务申请票据)

    操作：请求指定服务 /msdsspn:CIFS/DC.xiaorang.lab /ptt 。

    原理：MSSQLSERVER$ 再次联系 KDC ：“我现在要代表 Administrator 去访问域控的 CIFS 服务（文件共享），这是刚刚你给我的、带有可转发属性的 Administrator 的 TGS”。KDC 检查 Active Directory 属性，发现 MSSQLSERVER$ 确实被配置了到 CIFS/DC.xiaorang.lab 的约束委派权限 。验证通过，KDC 生成一张 Administrator 访问域控 CIFS 的最终 TGS，发给 MSSQLSERVER$。

  • 第四步：凭证注入与利用

    操作：Rubeus的 /ptt (Pass-The-Ticket) 参数直接将最后获取的高权限 TGS 注入到当前内存会话中

    原理：此时当前系统的上下文已经拥有了域管访问 DC 共享目录的合法票据，因此可以直接通过 dir \\DC.xiaorang.lab\c$ 列出并读取 flag04.txt ，完成对整个域环境的最终攻陷。

    SID History 属性滥用

    SID（安全标识符）是 Windows 系统中用于标识用户、组和计算机的唯一 ID。SIDHistory 属性的初衷是为了支持域迁移：当一个账号从 A 域迁移到 B 域时，系统会把该账号在 A 域的旧 SID 保存到新账号的 SIDHistory 属性中，这样用户就能无缝访问 A 域的原有资源。 漏洞产生于滥用：如果在同一个域内，攻击者能够将一个高权限组（如 Domain Admins，其 SID 结尾通常为 512）的 SID 写入到一个普通用户的 SIDHistory 属性中，那么当该普通用户登录时，其生成的访问令牌（Token）就会包含高权限组的 SID，从而直接“继承”了域管权限。

BadSuccessor 漏洞原理

BadSuccessor 攻击利用了 dMSA 中的“msDS-ManagedAccountPrecededByLink”属性。攻击者通过篡改该属性，模拟从高权限账户（如域管理员）到新创建的 dMSA 的“迁移”过程。此操作诱使密钥分发中心（KDC）向dMSA授予目标账户的完整权限，从而实现完全模拟攻击，且无需修改现有账户或组成员关系。

利用BadSuccessor漏洞的步骤

拥有最低权限的攻击者可按以下步骤实施攻击：

  • 创建dMSA：攻击者在拥有足够权限的 OU 内创建一个委托托管服务账户（使用 New-ADServiceAccount -DelegatedManagedServiceAccount 等命令）。
  • 修改关键属性：修改 dMSA 的 msDS-ManagedAccountPrecededByLink 属性，将其指向高权限账户（如域管理员账户的 DN）。
  • 以dMSA身份认证：系统将该 dMSA 视为高权限账户的合法继承者赋予其等效权限，最终实现域管理员权限的窃取。

RBCD 利用笔记：AddAllowedToAct 权限（普通用户对 DC 的 RBCD 案例）

场景：phantom.vl 域中，普通用户对 DC$ 拥有 AddAllowedToAct（即 msDS-AllowedToActOnBehalfOfOtherIdentity 写权限），域机器账户配额（MAQ）被设为 0，无法创建机器账户。最终通过 Forshaw 无 SPN RBCD 技巧 拿到 Administrator 的票据并 dump NTDS。

一、权限含义

AddAllowedToAct 本质是：对目标计算机对象的 msDS-AllowedToActOnBehalfOfOtherIdentity 属性拥有写权限。

  • 这个属性正是 RBCD（资源型约束委派） 的配置项。
  • 写入格式：一个安全描述符（Security Descriptor），其中 ACE 包含“被允许代表其他用户认证的服务账户”的 SID。
  • 效果：被写入的账户（如 wsilva / crose）可以对该计算机（如 DC$）执行 S4U2Proxy，冒充任意域用户（含 Administrator）。

项目 值 影响

关键难点：标准 RBCD 要求委派账户有 SPN（通常是机器账户）。MAQ=0 且只有普通用户时，必须使用 U2U + 修改 NT Hash 为 TGT 会话密钥 的绕过方法（James Forshaw, Exploiting RBCD Using a Normal User Account）。

三、攻击原理（Forshaw 技巧）

普通用户直接跑 S4U 会失败：

阶段 报错 原因
S4U2Self KDC_ERR_S_PRINCIPAL_UNKNOWN KDC 不知道用哪个密钥加密票据（用户无 SPN）
S4U2Proxy KDC_ERR_BADOPTION KDC 无法解密 S4U2Self 返回的票据

绕过思路：

  1. 用 U2U（User-to-User） 扩展请求 S4U2Self，让票据用 TGT 会话密钥加密。
  2. 在 S4U2Self 与 S4U2Proxy 之间，把该用户的 NT Hash 改成 TGT 会话密钥。
  3. 这样 KDC 在 S4U2Proxy 阶段用“用户长期密钥”解密票据时，正好等于会话密钥 → 解密成功 → 签发票据。

前提条件：

  • TGT 必须是 RC4（rc4_hmac），因为只有 RC4 会话密钥是 16 字节、可直接当作 NT Hash 写入。
  • TGT 必须带 forwardable 标志。
  • 目标账户（Administrator）不能是 NOT_DELEGATED 或 Protected Users。
  • 被牺牲的用户账户密码会被改掉（sacrificial account）。

六、常见报错与处理

报错 原因 处理
KDC_ERR_S_PRINCIPAL_UNKNOWN（S4U2Self） 用户无 SPN 改用 U2U（-u2u）
KDC_ERR_BADOPTION（S4U2Proxy） KDC 无法解密票据 / 会话密钥不匹配 确保 NT Hash = 原始 TGT 会话密钥；KRB5CCNAME 指向原始 TGT

七、要点总结

  1. AddAllowedToAct = 可写 RBCD 属性，是 RBCD 攻击的入口权限。
  2. MAQ=0 时，不要想着建机器账户，直接拿普通用户做 RBCD。
  3. 普通用户无 SPN → 必须走 U2U + 改 NT Hash 为 TGT 会话密钥 的 Forshaw 技巧。
  4. RC4 是硬前提，AES 会话密钥无法直接当 NT Hash 用。
  5. getST 必须用改密前的原始 TGT，这是最容易踩的坑。
  6. 牺牲账户密码会失效，事后需用有权限的账户重置恢复。
  7. 拿到 cifs/DC 票据后即可 secretsdump / --ntds 拿域管哈希，完成域控接管。
